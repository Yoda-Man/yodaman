# YodaMan Runtime Event Protocol

## Transport

Agent tasks stream events with Server-Sent Events from:

```http
POST /api/agent/task
```

The request body is:

```json
{
  "task": "Implement a login form",
  "projectId": "/absolute/project/path",
  "fileIds": ["optional-upload-id"]
}
```

`task` is required (up to 20,000 characters). `projectId` is optional. `fileIds` is optional: up to 20 ids returned by `POST /api/upload/temp`, attached to the task before it starts.

Each event is emitted as a JSON object in an SSE `data:` frame, and every event carries the task's `taskId`.

## Event Types

The protocol's event names are defined in `shared/protocol.schema.json` (`TASK_EVENT_TYPES`): `task_started`, `tool_start`, `tool_end`, `awaiting_approval`, `task_cancelled`, `final_answer`, and `error`. The runtime also emits two events that are not in that list, `upload_error` and `response_truncated`, described at the end of this section.

### `task_started`

Emitted immediately after the runtime accepts a task.

```json
{
  "type": "task_started",
  "taskId": "abc123",
  "projectId": "/absolute/project/path"
}
```

### `tool_start`

Emitted before a tool runs. Calls the runtime routes itself, without the model choosing a tool, also carry `"routed": "direct"`.

```json
{
  "type": "tool_start",
  "taskId": "abc123",
  "tool": "searchCode",
  "params": {
    "query": "auth service"
  }
}
```

### `tool_end`

Emitted after a tool completes. A rejected approval produces a `tool_end` whose `result` is `{ "error": "User rejected this change." }`, and the task continues.

```json
{
  "type": "tool_end",
  "taskId": "abc123",
  "tool": "searchCode",
  "result": {}
}
```

### `awaiting_approval`

Emitted when the agent wants to run any tool that is not on the read-only list in `shared/toolCapabilities.js` (file writes, patches, commands, OpenSpec changes, and plugins that declare a mutating permission), and needs human approval.

```json
{
  "type": "awaiting_approval",
  "taskId": "abc123",
  "tool": "writeFile",
  "params": {
    "filePath": "/absolute/path/file.js",
    "oldContent": "previous file content",
    "newContent": "proposed file content"
  },
  "impact": {},
  "specImpact": {}
}
```

For a tool that touches no file, `params.filePath` is `null` and `params.arguments` carries the tool's sanitised parameters. `impact` is the change's blast radius (dependents, tests, risk), and `specImpact` lists the OpenSpec specs that mention the file, when OpenSpec is available.

Clients should show a diff and then call:

```http
POST /api/agent/approve
```

With:

```json
{
  "taskId": "abc123",
  "approved": true
}
```

### `final_answer`

Emitted when the agent finishes.

```json
{
  "type": "final_answer",
  "taskId": "abc123",
  "answer": "Done."
}
```

### `task_cancelled`

Emitted when a task is cancelled. The stream then ends without a `final_answer`.

```json
{
  "type": "task_cancelled",
  "taskId": "abc123",
  "message": "Task cancelled."
}
```

### `error`

Emitted when a task fails.

```json
{
  "type": "error",
  "taskId": "abc123",
  "message": "Something went wrong."
}
```

### `upload_error` and `response_truncated`

`upload_error` (`taskId`, `fileId`, `message`) is sent before `task_started` when a `fileIds` entry cannot be attached; the task still runs without that file. `response_truncated` (`taskId`, `iteration`, `message`) is sent when Context Expert exited mid-answer and the answer was salvaged but is incomplete.

Neither is in `TASK_EVENT_TYPES`, so `isTaskEvent()` returns false for them and `assertTaskEvent()` throws.

## Cancellation

Clients can request cancellation with:

```http
POST /api/agent/cancel
```

Body:

```json
{
  "taskId": "abc123"
}
```

The task's status becomes `cancelling`, a pending approval is resolved as rejected, and the reasoning loop stops at the next cancellation check.

## Task State APIs

External clients can inspect recent persisted agent state with:

```http
GET /api/agent/tasks
```

Specific persisted task event histories are available with:

```http
GET /api/agent/tasks/:taskId/events
```

Mobile and secondary clients can inspect pending approvals with:

```http
GET /api/agent/pending-approvals
```

Task state is stored in the `tasks` table of `yodaman.db` (SQLite, in the user's data folder). If SQLite cannot be opened, the runtime falls back to `task-history.json` plus the append-only `task-history.jsonl` in the same data folder. The runtime keeps the 100 most recent tasks, each with at most its last 250 events. Either way, recent timelines can be replayed after a runtime restart.

Shared protocol constants are generated by `npm run generate:protocol` from `shared/protocol.schema.json` into `shared/yodamanProtocol.js`, with TypeScript declarations in `shared/yodamanProtocol.d.ts`.
