The Three-Tool Pillar

Three tools are mandatory, and YodaMan never consults one without the others. This is the architecture, not a feature list.

  • Context Expert — meaning. Semantic search and LLM reasoning over your indexed workspace. Powers search, the agent finding files, and RAG retrieval.
  • Graphify — structure. The local knowledge graph. Powers blast radius, centrality, proximity, and the structural half of ranking.
  • OpenSpec — intent. Architecture specs as a first-class input. Powers spec coverage, drift detection, and the propose/validate/archive workflow.

Search ranks by all three: semantic × 0.50 + proximity × 0.20 + centrality × 0.15 + specCoverage × 0.15. The agent receives a Stardust Brief every turn carrying graph state, spec awareness, and per-file impact. Planning follows Propose → Validate → Archive with drift checking.

Stardust

Stardust is where the three tools become visible as one system. Eight tabs, backed by a WebSocket feed that watches openspec/ for changes.

  • Board — real-time OpenSpec change board with task progress, validation health, and a side-by-side spec diff grouped by ADDED/MODIFIED/REMOVED/RENAMED.
  • Drift — current workspace state compared against active specs, with severity badges and a one-click reindex.
  • Compose — what every tool knows about one file: which specs describe it, its structural position, and how Context Expert ranks it.
  • Trust — per-tool health plus the overall WorkspaceReadiness verdict, with a live activity feed.
  • Trace — why each search result ranked where it did, showing all four signals and their weights per result.
  • Diagnostics — index freshness, graph state, OpenSpec CLI status, plugin health, and workspace connectivity in one status grid.
  • Commands — every tool execution with sanitized parameters, timing, exit codes, and result summaries.
  • Impact — blast radius for any file at a configurable hop depth of 1 to 4, with dependents, spec breakdown, risk verdict, and per-file test coverage.

Ecosystem Architecture

One shared local runtime serves the web UI, desktop app, VS Code extension, mobile companion, and CLI.

  • The runtime owns agent execution, tools, indexing, sessions, plugins, audit, and safety policy.
  • Graphify builds the knowledge graph locally, using Ollama for enrichment, and feeds graph-aware answers, impact analysis, and architecture maps.
  • Clients own UX: editor actions, desktop control, and mobile approvals.
  • REST plus SSE for task event streams, and a WebSocket for the live Stardust feed.

Security And Audit

The runtime hardens local agent tools by default.

  • File and command paths resolve against configured workspace roots before anything runs.
  • Shell operators (; & | ` $ > <) are rejected outright — one command at a time. Executables must be bare names drawn from an allowlist, not paths.
  • Every file write pauses for a structured approval showing the diff, the files that depend on it, and whether any test covers the change.
  • Tool calls are recorded with status, duration, sanitized parameters, and result summaries.
  • Pairing-token enforcement for non-local clients, plus a cross-site request policy on the runtime.

Mobile Linking

The phone must connect to the host machine's LAN address, not 127.0.0.1.

curl -X POST http://127.0.0.1:3090/api/pairing \
  -H "Content-Type: application/json" \
  -d '{"runtimeUrl":"http://YOUR-LAN-IP:3090"}'

Paste the returned yodaman://pair deep link into the mobile app and tap Use Pairing Link.

Downloads and Updates

YodaMan gives you a choice of clients so you can work from the environment that fits the moment.

  • Desktop downloads are available directly for macOS and Linux. Windows installers are published as build artifacts from a native Windows runner — see the Windows card on the downloads page.
  • The VS Code extension is available on the Visual Studio Marketplace, or as a VSIX for offline installs.
  • Mobile companion clients help you monitor tasks and approve changes while away from your desktop. Pair over your LAN; there is no app-store build yet.

API Reference

Runtime endpoints are mounted under /api. The most useful ones:

Agent

  • POST /api/agent/task — start a task
  • GET /api/agent/tasks — list tasks
  • GET /api/agent/tasks/:taskId/events — SSE event stream
  • GET /api/agent/pending-approvals — approvals awaiting a decision
  • POST /api/agent/approve — approve or reject
  • POST /api/agent/cancel — cancel a running task

Search and graph

  • GET /api/search — ranked search across indexed workspaces
  • GET /api/graphify/status — graph state
  • GET /api/graphify/map — architecture map
  • POST /api/graphify/affected — blast radius for a file
  • POST /api/graphify/explain — explain a node or relationship

Stardust

  • GET /api/stardust/board — change board
  • GET /api/stardust/drift — drift report
  • GET /api/stardust/compose — cross-tool view of one file
  • GET /api/stardust/deltas/:name — spec diff for a change
  • PUT /api/stardust/validation/:name — validate a change
  • GET /api/stardust/diagnose — runtime diagnostics
  • WS /api/stardust/live — live dashboard feed

Runtime

  • GET /api/health — dependency health
  • GET /api/readiness — WorkspaceReadiness verdict
  • GET /api/policy — active command policy
  • GET /api/audit — audit log
  • GET /api/plugins — installed plugins
  • POST /api/pairing — issue a pairing token

Choosing A Client

Use the desktop app when you want the full control center, the VS Code extension when you are actively coding, and mobile when you only need oversight away from the keyboard.

  • Desktop: manage projects, plugins, indexing, sessions, model settings, runtime health, and approvals.
  • VS Code: ask workspace questions, run coding tasks, review diffs, and keep streamed tool events beside your editor.
  • Mobile: monitor tasks, search projects, ask workspace questions, and approve or reject pending changes.
